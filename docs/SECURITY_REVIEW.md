# TripKing — security review (Phase 6, backend lane)

> Living doc. Started when the `/admin` `X-Admin-Key` stopgap was replaced with a `role=admin` Bearer check (commit `feat(admin): …`). Owned by the backend lane; update it as Phase-6 items land.

## Threat model in one paragraph

The browser never touches Postgres directly — every request goes through the Supabase Edge Functions (`/functions/v1/<name>`), which run with the **service-role key** (RLS-bypassing) and therefore **must enforce access control themselves**. Each function validates the caller's Bearer access token via GoTrue (`db.auth.getUser(token)` → `auth.uid()`), looks up `public.users.role`, and then applies owner / poster / assigned-driver / `role==='admin'` rules that **mirror the RLS policies in migrations 002/003** (the RLS policies are now "documentation of intent" + a defence-in-depth net if a query ever runs under the anon key). Public reference/content reads (`/admin/<list>` GET, `/drivers`, `/vacancies`, published `/reviews`, …) are intentionally unauthenticated.

## RLS-coverage audit — edge-function check ↔ RLS policy

| Resource (function) | Migration RLS policy | Function-level enforcement | Verdict |
|---|---|---|---|

**No gaps found** in the function-level checks vs the RLS intent. Two intentional divergences (driver KYC column is admin-only despite owner-update RLS; review *report* is open to any authed user despite admin-only update RLS) are noted above and are by design.

## Authentication notes

- **Bearer everywhere for writes.** Access token from `POST /auth/verify-otp` (~1 h), refresh token (~30 d), 401 → single-flight `POST /auth/refresh` in the `apiClient`. The `apiClient` carries `Authorization: Bearer …` when signed in; otherwise `X-API-Key` for public reads.
- **`/admin/*` now requires `role==='admin'`** (not the old `X-Admin-Key` env secret). The `ADMIN_API_KEY` env secret on the `admin` function and in `.env.development` is now unused (safe to remove). This also **fixes the `/administration/config` UI** — its writes now succeed when an admin is signed in (the `apiClient` already sends the Bearer).

## Account / profile deactivation — the `is_active` kill switch (migration 017)

Two distinct levels, both checked server-side (the flag must be honoured everywhere — that was the explicit ask):

- **Profile-level — `drivers.is_active` / `trip_managers.is_active`** (default `true`). Flipped by an admin via `PATCH /drivers/:id/active` / `PATCH /agents/:id/active { is_active, reason? }` (admin-only; sets `deactivated_at`/`deactivation_reason`/`deactivated_by`; writes an `admin_audit_log` row with `actor_user_id`; fires an `account_status_change` notification to the affected user — a new `notifications.type` value). A deactivated profile: 404s on `GET /drivers|/agents/:id` for everyone but its owner and admins; drops out of the default `GET /drivers|/agents` list (`?active=false` shows only deactivated, `?include_inactive=true` shows all); is still returned by `GET /drivers|/agents/me` (with `is_active:false`, so the frontend can show a "suspended" banner); its vacancies disappear from `GET /vacancies` and never match alerts (`match_alerts_for_vacancy` returns 0 for a deactivated driver's vacancy; `match_alerts_for_trip`/`_vacancy` also skip alerts whose owner's driver/agent profile is deactivated); and the owner gets a **403 `ACCOUNT_SUSPENDED`** on `POST /vacancies`, `POST /trips`, `POST /trips/:id/applicants`, `POST /reviews`. The poster can't assign a deactivated driver — `POST /trips/:id/assign` → **422** ("pick another applicant"). In-flight (assigned / in-progress) trips are intentionally **left alone** — no auto-cancel. Orthogonal to `kyc_status` (a `kyc_status='rejected'` driver and a deactivated driver are independent states).
- **Account-level — `users.is_active`** (default `true`; vestigial column, now wired). When `false`, `/auth verify-otp` and `/auth refresh` return **403 `ACCOUNT_SUSPENDED`** — the account can't get a (new) session at all (a still-valid access token expires within ~1 h, and the next refresh fails). This is the harder switch (vs. profile deactivation, where the user can still sign in and see the banner). **There is no admin endpoint to set `users.is_active` yet** — it's flipped via SQL for now; a `PATCH /admin/users/:id` (or extending `/active` to optionally cascade to the `users` row) is a natural follow-up. Documented here so it isn't forgotten.

Smoke coverage: `test-drivers.cjs` (the `/active` endpoint + 404-for-strangers + `?active=false`/`?include_inactive=true` + `…/me` still returns it + non-admin 403), `test-vacancies.cjs` (403 on post + vacancies hidden + reactivation restores them), `test-trips.cjs` (apply 403 + assign 422), `test-reviews.cjs` (review 403). The `users.is_active` → `verify-otp` 403 path was verified manually (flip via `db.cjs`, re-`verify-otp` → 403) — not in a smoke since there's no endpoint to set it.
